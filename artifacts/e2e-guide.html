Read this before you record anything Three things in this system work end to end: the charge → QR → real finalized on-chain payment → verified paid verdict rail; the injection/negative drills; and the 225-test suite. Three things do not: no relay has ever been energized by this code, no attestation has ever been signed or landed on chain, and the SOP loop cannot self-execute. Every command and every spoken line in this guide is built only from the first group. Claiming the second group on camera is the single fastest way to lose credibility on an otherwise strong submission.
Which machine runs what — read once, then trust the badges Every terminal block in this guide is stamped with the machine it belongs to. MAC is your laptop. RASPBERRY PI is over SSH.

Sections 02 through 08 are 100% Mac. The entire ProofKiosk demo — build, tests, plugins, charge, payment, watch, attest, every injection drill — runs on your laptop and never touches the Pi. The Pi appears only in §10–11, and only as optional B-roll. If your Pi never boots, you still have a complete demo.

01Where the plugins actually run

Short answer to the question you asked: the plugins run inside the ZeroClaw host process, not separately — and you should not use the desktop dashboard for the demo.

YOUR TERMINAL ZEROCLAW HOST PROCESS (one binary) ───────────── ──────────────────────────────────────── ┌──────────────────────────────────────┐ zc agent ────────────────────►│ agent loop ──► LLM (reformats!) │ │ │ │ exact-host-runtime-smoke.sh ─►│ WasmTool runtime (wasmtime) │ │ │ │ │ ┌────▼─────┬──────────┬─────────┐ │ │ │ charge │ watch │ attest │ │ ← .wasm components, │ │ .wasm │ .wasm │ .wasm │ │ fresh store per call │ └──────────┴────┬─────┴────┬────┘ │ └────────────────────┼──────────┼──────┘ ▼ ▼ Solana RPC unsigned tx (nobody signs it)
QuestionAnswer
Separate processes / servers per plugin?No. Three .wasm components loaded by the one zeroclaw binary. Nothing to start, nothing listening on a port.
Inside the zeroclaw desktop dashboard?No — and don't. The companion app exists (zeroclaw desktop, menu-bar + dashboard) but adds nothing here and puts a UI between you and the evidence.
So what do I drive on camera?The CLI. Two entry points, and the difference matters (below).
Do plugins keep state between calls?No. The host builds a fresh WASI store per execute. A static counter silently resets — which is exactly why single-use delivery is read back off the chain.
The one distinction that decides your evidence quality zc agent --message "..." routes through the LLM. Good for showing the product — a human asks, the agent calls a tool. But the model can reformat tool output, so it is presentation evidence, never trusted input.
./scripts/exact-host-runtime-smoke.sh executes the component through the real pinned WasmTool and writes the raw WIT ToolResult to disk. That file is the security boundary. Use it for anything you assert as proof.

02Pre-flight — five commands

cd /Users/vyapar/Downloads/proofkiosk rustc --version # expect 1.97.1 solana --version # expect 4.1.1 spl-token --version # expect 5.6.1 node --version # expect v24.10.0 zeroclaw plugin --help
The last one is the gate. On the stock zeroclaw 0.8.3 on your PATH it prints unrecognized subcommand 'plugin' — that binary has no WASM plugin runtime and will never load ProofKiosk. Phase 1 fixes it. Do not proceed past that error.

03Phase 1 — build the plugin-capable pinned host

./scripts/install-pinned-zeroclaw.sh # once per machine, ~10 min of cargo source scripts/demo-env.sh # ONCE PER TERMINAL — see the box below
The installer checks out exact commit e112ce6b (identifies as 0.8.2), builds with --locked + plugins-wasm-cranelift, and proves the result exposes plugin. demo-env.sh then puts that pinned binary ahead of the stock one on PATH, exports PROOFKIOSK_ROOT / ZEROCLAW_SRC / ZC_CONFIG_DIR / ZC_AGENT / ITEM_ID, defines the zc() helper, and re-loads .devnet/payment.env if setup already ran. It prints the resolved version so you can see at a glance you are on 0.8.2, not 0.8.3.
The single most likely thing to go wrong zc is a shell function and the pinned host is a PATH edit. Neither survives closing the terminal, opening a new tab, or a split pane. Symptom: zsh: command not found: zc, or unrecognized subcommand 'plugin' because PATH fell back to the stock 0.8.3 binary.
Fix, every new terminal: cd to the repo and source scripts/demo-env.sh. Nothing is lost — it is idempotent and re-reads any existing setup state.
Do not paste the environment block out of this PDF. Long names like $PROOFKIOSK_ROOT split across line breaks when copied from a PDF and arrive as $PROOFKIOSK + ROOT, which fails in confusing ways (command not found: discover, stray sudo usage errors). Sourcing the script is one short line precisely so this cannot happen.

06Phase 4 — build the test environment

( set -o pipefail MODE=localnet MINT_AMOUNT=1000 ./scripts/devnet-setup.sh \ | tee "$PROOFKIOSK_ROOT/.devnet/setup-localnet.txt" ) source "$PROOFKIOSK_ROOT/.devnet/payment.env" ./scripts/check-config.sh "$PROOFKIOSK_CONFIG" spl-token balance "$PROOFKIOSK_MINT" --owner "$PROOFKIOSK_MERCHANT" --url "$PROOFKIOSK_RPC_URL" # 0
Creates separate merchant and customer wallets, funds both, creates both token accounts, mints the fake 6-decimal token only to the customer, creates the durable nonce account, and writes a validated .devnet/zeroclaw.toml. It passes --url on every call and never mutates your global Solana config. check-config.sh catches the two silent killers: device_authority ≠ nonce_authority (markers never authenticate → single-use quietly dies) and drifted price_list (real payments read as mismatches).
Run localnet first. Only switch MODE=devnet once this is green.
Rate limits will bite you on camera Public Devnet RPC is throttled and the faucet allows ~2 anonymous requests / 8 h (sign in with GitHub to raise it). An RPC 429 is not a payment result — verify the address in Explorer and retry. Do the funding well before you hit record.

07Phase 5 — the end-to-end run

5.1 · Charge — through the real host, not the chat

export CHARGE_TOOL_RESULT="$PROOFKIOSK_ROOT/.devnet/charge-tool-result.json" ZEROCLAW_SOURCE_DIR="$ZEROCLAW_SRC" PROOFKIOSK_HOST_OUTPUT="$CHARGE_TOOL_RESULT" \ ./scripts/exact-host-runtime-smoke.sh test -s "$CHARGE_TOOL_RESULT"
Writes the raw WIT ToolResult. output is a string containing the versioned charge object ({"v":1,...,"status":"created"}). It refuses to overwrite a prior result — that is deliberate, so you cannot silently regenerate evidence.
export PAY_URL="$(node scripts/trusted-charge-handoff.mjs \ --input "$CHARGE_TOOL_RESULT" --config "$PROOFKIOSK_CONFIG" \ --orders-dir "$PROOFKIOSK_ROOT/.proofkiosk/orders" --url-only)" export REFERENCE="$(node -e 'console.log(new URL(process.argv[1]).searchParams.get("reference"))' "$PAY_URL")" test -f "$PROOFKIOSK_ROOT/.proofkiosk/orders/$REFERENCE.json"
Re-validates the raw result against the plaintext operator config and persists a durable order record with immutable quote economics and quote time. This is what later rejects a payment that lands after expiry, or a catalog edited after the quote.
./skills/kiosk-qr/render-qr.sh "$CHARGE_TOOL_RESULT" "$PROOFKIOSK_CONFIG" \ "$PROOFKIOSK_ROOT/.devnet/payment.png" open "$PROOFKIOSK_ROOT/.devnet/payment.png"
cameraThe renderer repeats the trusted validation — it will not accept an arbitrary solana: URL. The QR can only come from a real host result.

5.2 · Watch before payment

zc agent --agent "$ZC_AGENT" --temperature 0 \ --message "Call kiosk_watch exactly once with {\"reference\":\"$REFERENCE\",\"item_id\":\"$ITEM_ID\"}. Return the complete raw tool output unchanged."
cameraExpect status:"pending", success:false. If you get mismatch, something already touched that public reference — generate a fresh charge.

5.3 · Pay — real, finalized, independently validated

( set -o pipefail; npm run devnet:pay | tee .devnet/payment-submit.txt ) export PAYMENT_SIG="$(awk '/^submitted / {print $2; exit}' .devnet/payment-submit.txt)" grep -F "finalized and validated $PAYMENT_SIG" .devnet/payment-submit.txt
cameraBuilds a reference-bearing SPL transfer with the official Solana Pay package, preserves the charge's PKPAY1 memo binding reference+item, submits from the separate customer key, waits for finalized, then calls validateTransfer over recipient/mint/amount/reference. Known-good localnet run: merchant 0 → 1.5, customer 1000 → 998.5.

5.4 · Watch after payment — the money shot

spl-token balance "$MINT" --owner "$MERCHANT" --url "$RPC_URL" # now 1.5 zc agent --agent "$ZC_AGENT" --temperature 0 \ --message "Call kiosk_watch exactly once with {\"reference\":\"$REFERENCE\",\"item_id\":\"$ITEM_ID\"}. Return the complete raw tool output unchanged."
camerastatus:"paid", success:true. Verified at finalized commitment against the operator's merchant, mint, price, and the PKPAY1 memo — with no amount argument anywhere in the call.

5.5 · Attest — stops exactly where it should

zc agent --agent "$ZC_AGENT" --temperature 0 \ --message 'Call kiosk_attest exactly once with {"kind":"reading","metric":"temp_c","value":4.2}. Return the complete raw tool output unchanged.'
cameraReturns signature_required plus unsigned message bytes. This is the correct, honest ending — the plugin builds a Memo+System-only durable-nonce transaction and hands it to an external signer that this repo deliberately does not ship.

5.6 · Heartbeat & SOP validation

zc agent --agent "$ZC_AGENT" --temperature 0 \ --message 'Call kiosk_watch exactly once with {"mode":"heartbeat"}. Return the complete raw tool output unchanged.' zc config set sop.sops_dir "$PROOFKIOSK_ROOT/sops" zc sop validate zc sop graph proofkiosk-payment-loop --format outline
Heartbeat target/authority/threshold are all operator config, never arguments; a fresh deployment correctly returns missing until an authenticated attestation lands. sop validate proves syntax only — say so out loud if you show it.

09Channels — pick one; the plugins do not care

Before you touch this section If you have ever pasted a bot token into a chat, a terminal, a file, or a screenshot, treat it as burned. Message @BotFather → /revoke, pick the bot, and use the fresh token. A leaked token lets anyone send and receive as your bot — including while you are on camera.

Everything so far works in a local shell. A chat channel is worth the fifteen minutes because it turns the abstract claim into the actual threat model: a stranger, in a chat window, talking to an agent that can move money. An injection typed into your own terminal is a demo. The same injection typed from a phone into a public bot is the argument.

The plugins are structurally channel-blind — and you can prove it on camera This is not a design promise, it is enforced by the component boundary. The plugins build against world tool-plugin { import logging; export plugin-info; export tool; } — they import only logging. There is no channel interface in their world at all, so a plugin cannot discover whether a request arrived from Telegram, Discord, a webhook, or a local shell. Grep the sources for telegram, discord, whatsapp, chat_id: zero hits across plugins/*/src and crates/*/src. The only matches in the repo are in the vendored upstream wit/channel.wit, a world ProofKiosk does not use.

Cheapest high-value shot in the whole video: run the same sale on two channels, show the tool output is byte-identical, then cut to that one-line world declaration. Swapping channels is a config command — no rebuild, no code change, no re-test.

10Your Raspberry Pi 3B+ — honest scope

Do not build ZeroClaw on a 3B+ The bill of materials targets a Pi 4 with 2 GB+. A 3B+ has 1 GB, and ZeroClaw pulls in wasmtime and cranelift — a large Rust build. On 1 GB with no swap it will either be killed by the OOM reaper or grind for many hours, and it buys you nothing: even a successful Pi build does not create relay_pulse or bme280_read, because those tools do not exist in this repository yet. Do not try it before a deadline.

The Pi's entire job in this demo is to be photographed and to prove the I²C bus works. That is a genuine, honest contribution to the video — it shows the hardware is real — and it costs about fifteen minutes instead of a lost night.

9.1 · Flash the card (Mac, Imager already on your SD)

You said the 64 GB card already has Raspberry Pi OS Lite written by Imager. Lite is headless — no desktop — so the one thing that matters is that SSH and Wi-Fi were preconfigured. In Raspberry Pi Imager that is the gear / “Edit Settings” screen before writing:

  • Set hostname → proofkiosk
  • Set username + password (there is no default pi/raspberry any more)
  • Configure wireless LAN → your 2.4 GHz SSID — a 3B+ has no 5 GHz-only radio issues, but it does not do Wi-Fi 6; use the same network as your Mac
  • Services → Enable SSH → password authentication

If you wrote the card without that screen, re-flash with it. It is far faster than recovering a headless Pi you cannot reach. Choose the 64-bit Lite image — the 3B+ supports it.

9.2 · First contact

ping -c 3 proofkiosk.local ssh <your-username>@proofkiosk.local
Run this on the Mac. Insert the card, connect power, wait ~60 s for first boot. If .local fails, find the Pi's IP from your router's client list and ssh user@192.168.x.x. Everything after this point is typed inside that SSH session.

9.3 · Enable I²C and confirm the sensor

sudo raspi-config # Interface Options → I2C → Yes → Finish → reboot sudo apt-get update && sudo apt-get install -y i2c-tools i2cdetect -y 1 # BME280 answers at 0x76 or 0x77
cameraThis is your best hardware shot: a real address appearing in the grid proves the sensor is wired and the bus is alive. It is honest — it claims nothing about ProofKiosk driving it. If the grid is all --, check 3.3 V (not 5 V) on VIN, and SDA/SCL on pins 3/5.

9.4 · Optional: blink an LED (not ProofKiosk code)

pinctrl set 17 op dh # GPIO17 high — LED on pinctrl set 17 op dl # GPIO17 low — LED off
On older Pi OS releases the tool is raspi-gpio set 17 op dh instead. Wire the LED through a resistor (330 Ω–1 kΩ) from GPIO17 to ground — never a bare LED, and never a solenoid.
Say clearly on camera that this is a bench indicator, not the product. It proves the pin toggles; it does not mean ProofKiosk drove it, because relay_pulse does not exist.
